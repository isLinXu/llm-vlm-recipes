00执行摘要：九个关键判断

最重要的一条，来自你给的起点 recipe 本身

该文第 6 节明确承认：预训练模型 + 一句 system message，无需任何训练，也能生成正确答案，并称其为「viable alternative to fine-tuning」。整篇教程的目标其实只是让输出格式变简短。因此使用这套 cookbook 的第一步，不是选 LoRA 参数，而是先做 prompting / RAG 基线，并定义「微调相对基线的增量」——否则很可能花 A100 的算力去换一句 prompt 就能拿到的东西。

  1. Recipe 是教学样本，不是生产配方。几乎所有篇目都只用 1%–10% 数据、1–3 epoch、0.5B–7B 模型；评估多为单样本定性「vibe-check」，极少有 compute_metrics、准确率或 benchmark 数字。
  2. 技术主轴已经迁移。2023 年的 PEFT / SFT / 单卡 QLoRA，到 2024 年的 DPO，再到 2025–2026 年的 GRPO、MPO、GSPO、vLLM 在线生成、OpenEnv 多轮 Agent RL。Cookbook 的「Latest notebooks」几乎全是 RL / 在线训练。
  3. VLM 与 LLM 的差异不在算法，而在数据契约与 processor。顶层 images 列、content 必须是 list[dict]、processing_class=processor 而非 tokenizer、max_length=None 防止图像 token 被截断。这四点决定 80% 的 VLM 训练失败。
  4. QLoRA 是事实标准，但文字与代码常常不符。NF4 + double quant + r=8 出现在几乎所有 SFT/DPO/MPO 篇；SmolVLM / Granite / MPO 三篇实际启用了 use_dora=True，正文却仍写 LoRA / QLoRA。
  5. GRPO 系 recipe 的真正差异是 reward 工程。从 2 个二值函数（format + accuracy）→ 4 个渐进打分函数 → 环境标量 reward；而 reward 的「失败路径」设计（Wordle 中 invalid move 也拿 partial credit）比算法选择更决定结果可信度。
  6. 在线训练的瓶颈是 rollout 生成，不是梯度。官方实测单 GPU 上 use_vllm=True, vllm_mode="colocate" 达 0.07 it/s vs 关闭时 0.04 it/s（约 +75%）；max_completion_length 增到 1024 时差距扩大到 0.04 vs 0.02 it/s（+100%）。
  7. TRL 是算法原语层，不是万能框架。其 v1 taxonomy 已把 PPO 移除，稳定层只剩 SFT / DPO / KTO / GRPO / RLOO / Reward / Distillation，大量新方法放在 trl.experimental。它给的是「正确的原语」，不是「调好的默认值」。
  8. 复现风险集中在版本与代码瑕疵。多篇要求 pip install git+https://github.com/huggingface/trl.git（dev 版本），且存在 W&B/trackio 文字不一致、dict 切片、重复 keyword、processor 变量混用等可运行性问题（详见第 8 章）。
  9. 合理路径是逐级加码：prompting / RAG 基线 → SFT（格式与领域适配）→ 偏好优化（风格与对齐）→ 仅在有可验证奖励（数学、代码、规则环境）时才上 RL。绝大多数业务需求停在第 2 步。

02方法分类学：后训练谱系与 TRL v1 定位

把 20+ 篇 recipe 放到同一张方法谱系里，差异立刻清晰：数据形态决定 trainer，验证信号决定算法上限。

层级方法需要的监督信号对应 Cookbook recipe典型代价
L0 不训练Prompting / RAG / 结构化生成无三篇 multimodal RAG、structured_generation近乎为零
L1 监督微调SFT / QLoRA / DoRA / Prompt Tuning / FIM 续训输入-输出对vlm_trl、smol_vlm_sft、granite_vision、grounding、xLAM、code_llm低，单卡可行
L2 离线偏好DPO / KTO / ORPO / MPOchosen + rejected 成对偏好vlm_dpo_smolvlm、vlm_mpo、preference 数据集 recipe中，需偏好数据
L3 在线 RLGRPO / RLOO / GSPO / Online DPO可计算 reward（规则、verifier、环境）llm_grpo、vlm_grpo、grpo_vllm、advanced_reward、wordle高，rollout 占 80%+ 时间
L4 奖励建模 / 蒸馏RewardTrainer / GKD / Distillation偏好或教师分布Cookbook 中暂无独立 recipe高

2.1 TRL 官方 taxonomy（v1，2026 年现状）

来自 TRL 文档首页，这是判断「哪些方法算稳定」的一手依据：

稳定层

Online：GRPOTrainer、RLOOTrainer

Reward modeling：RewardTrainer

Offline：SFTTrainer、DPOTrainer、KTOTrainer

Distillation：DistillationTrainer

experimental 层

A2PO、AsyncGRPO、GMPO、OnlineDPO、CPO、ORPO、BEMA、GKD、GOLD、IWOPD、SDFT、SDPO、AsyncDistillation…

无稳定性保证，API 可能随版本变动

PPO 已经不在列表里

TRL v1 的 taxonomy 中没有 PPOTrainer / PPOConfig。跨源检索亦指向 v1.13 起移除经典 PPO 全栈、把 DPO/KTO/GRPO/JSD loss 统一收进 trl.losses。若你的方案仍基于「TRL + PPO + Critic」写就，需要重新核对依赖版本；这也是「别把旧博客当当前文档」的典型例子。

2.2 VLM 对齐的方法动机（官方博客口径）

TRL VLM Alignment 解释了为什么 2025 年后 VLM recipe 集体从 SFT/DPO 转向 MPO/GRPO/GSPO：

  • SFT 做推理任务会受 distribution shift 影响；DPO 对齐的模型可能无法生成连贯 rationale 并出现重复回答。
  • MPO 不是新 trainer，而是 DPOTrainer 的组合损失：loss_type=["sigmoid","bco_pair","sft"] + loss_weights=[0.8,0.2,1.0]，融合 DPO 偏好、BCO 质量、SFT 生成三类目标。论文报告 MathVista +6.2 pts（该数字来自论文，非 cookbook 复现）。
  • GSPO 不是独立 trainer，是 GRPO 的 loss 变体，把 importance sampling 从 token 级改到 sequence 级（importance_sampling_level="sequence"），对 MoE 更稳，因此自动继承 VLM 支持。
  • GRPO 相对 PPO 去掉 value model，组内相对奖励平均掉 reward noise，适合规则可验证任务。
口径提醒

该博客明确标注其模型输出对比只是 vibe-check：minimal runs、dataset subsets、不同数据集，「comparison is made for vibe-check」，不能当作方法优劣的定量结论。

def format_data(sample):
    return {
        "images": [sample["image"]],
        "messages": [
            {"role": "system", "content": [{"type": "text", "text": SYSTEM}]},
            {"role": "user", "content": [
                {"type": "image", "image": sample["image"]},
                {"type": "text", "text": sample["query"]}]},
            {"role": "assistant", "content": [{"type": "text", "text": sample["label"][0]}]},
        ]}

trainer = SFTTrainer(
    model=model,                       # 4-bit 量化后的 VLM
    args=SFTConfig(max_length=None, bf16=True, learning_rate=2e-4, ...),
    train_dataset=train_dataset, eval_dataset=eval_dataset,
    peft_config=LoraConfig(r=8, lora_alpha=16, target_modules=["q_proj","v_proj"]),
    processing_class=processor,        # 注意：processor，不是 tokenizer
)
trainer.train()

4.2 VLM 特有的六个工程要点（跨 recipe 归纳）

① 数据契约：images 是顶层列

TRL 官方规定 VLM 数据集必须有 images（PIL 列表）或 image（单图）顶层列，与 prompt/chosen/rejected 并列；消息 content 必须是 list[dict]，用 {"type":"image"} 占位。

② 防止图像 token 被截断

官方示例直接写 SFTConfig(max_length=None)，注释为「avoid truncation that may remove image tokens」；GRPO 侧对应 max_prompt_length=None。起点 recipe 与 SmolVLM 也都设了 max_length=None。

③ processing_class 传 processor

Qwen 系用 Qwen2VLProcessor / AutoProcessor；SmolVLM / Granite 用 AutoProcessor，Granite 甚至传 processor.tokenizer 配自定义 collator。传错对象是最常见的 VLM 训练报错源。

④ 图像统一 RGB

DPO / MPO / SmolVLM / Granite 都显式做 if image.mode != "RGB": image.convert("RGB")。部分模型（Idefics3）还要求 image_inputs 是嵌套列表 [[image]]。

⑤ 视觉塔的冻结 / 跳过量化

Granite recipe 用 llm_int8_skip_modules=["vision_tower","lm_head"] 跳过对视觉塔与输出头的量化；LoRA target 也常只筛 language_model 下的 _proj。跨源信息提示：vLLM 路径下无法对 vision/encoder 层做 LoRA，需 finetune_vision_layers=False。

⑥ label masking 要自己做时

Granite 与 PaliGemma grounding 两篇绕过 TRL 默认 dataset preparation，用 dataset_kwargs={"skip_prepare_dataset": True} + remove_unused_columns=False + 自定义 collate_fn，手工把 prompt / 图像 token 置为 -100，只对 assistant 回答或 suffix 计 loss。

4.3 两篇「非标准输出」recipe 的独特价值

Grounding（PaliGemma 2 + RefCOCO）把 bbox 编码成文本 token 而非数值回归目标，是 VLM「结构化输出即任务头」的范例：

# 归一到 1024，顺序是 y1, x1, y2, x2（不是常见的 xyxy）
def format_location(value, max_value):
    return f"<loc{int(round(value * 1024 / max_value)):04}>"
# 训练 suffix: <loc0312><loc0423><loc0967><loc0609> middle vase
# 多个结果用 " ; " 分隔；processor(text=prompts, images=..., suffix=suffixes)

它同时暴露了一类典型文档风险：正文说 bbox 是 xyxy，增强用 A.BboxParams(format="coco")，转换函数又按 [x,y,w,h] 处理；训练 prompt 是 "<image>Detect {caption}."，推理却是 "<image>detect {caption}"（大小写与句号不一致）。复现前必须核对。

Granite Vision 的自定义 collator 展示了「只对 assistant 输出算 loss」的通用做法：扫描 input_ids，遇到 <|assistant|> 开始计 loss，遇到 <|end_of_text|> 关闭。任何需要精细控制监督范围的 VLM 任务都可复用这个骨架。

5.2 Reward 工程：真正的差异化所在

基础版：2 个二值 reward

format_reward：正则 ^<think>.*?</think>\s*<answer>.*?</answer>$ → 1.0 / 0.0

accuracy_reward：math_verify.parse/verify + LatexExtractionConfig()，extraction_mode="first_match"。gold 不可解析时给 1.0（宽松兜底），verify 异常给 0.0。

效果：模型学会格式，但答案仍错。基础 recipe 自承「solution itself is incorrect」。

进阶版：4 个渐进打分 reward

GSM8K + 自定义 <start_working_out> / <SOLUTION> 标签。

精确格式 3.0；近似格式每 token ±0.5（合计 ±2.0）；答案正确性 3.0 / 1.5（±10%）/ 0.5（±20%）/ −0.5；数字抽取 1.5。

合计上限 9.5。未显式设 reward_weights，权重靠函数内分值实现。

Wordle Agent RL：reward 的「失败路径」陷阱

环境对真正解出单词支付 ENV_SOLVED_REWARD = 1.0，但重复提交非法走法导致 early terminate 时也会支付 partial credit。所以 reward > 0 根本不等于赢；一个总猜六字母单词的小模型可能从未解题却拿到「漂亮」的分数。正确做法是 solved = bool(env.done and reward >= ENV_SOLVED_REWARD)，并同时报告 invalid-move rate。原文金句：「A metric that can only move in the flattering direction is not a measurement.」

其余工程要点：训练与评估必须 prompt parity（用 env_tools(env) 从环境类反射出 tool schema，避免测到 prompt mismatch）；环境返回 cumulative transcript，wrapper 要按 full[len(self._last_full_feedback):] 取增量反馈；评估环境跨多局复用，只在 finally 里 close 一次，中途 close 会撕掉 WebSocket。

5.5 另外三种「训练工程」recipe

xLAM function calling（QLoRA SFT）

把 60k 条 query/tools/answers 拼成 <user>…</user> <tools>…</tools> <calls>…</calls> 文本。Llama-3-8B，bs16×8=128、lr 1e-4、max_steps 1000、max_length 2048、optim="adamw_8bit"、LoRA r16 α16 挂 7 个 linear target。标称 16–24GB 可跑（示例环境却是 H100 100GB）。

注意：用 str(tool) 而非 json.dumps，产出是类 Python dict 文本，不是严格 JSON；评估只有 3 条定性样例。

单 GPU 代码 LLM（StarCoderBase-1B）

streaming=True + 自实现 ConstantLengthDataset（SEQ_LENGTH=2048、实测 chars/token=2.43）+ FIM 变换（FIM_RATE=0.5、FIM_SPM_RATE=0.5）。NF4 + LoRA r8 α32 dropout=0，仅训 0.486% 参数；lr 5e-4、cosine、warmup 30、max_steps 2000。用 prepare_model_for_kbit_training() 预处理。

这是少数把「数据打包效率」讲透的一篇。

RapidFire 并发多配置 SFT

单 GPU 上用 chunk-based scheduling 交错 4 组配置（LoRA r8/r32 × lr 5e-4 linear / 2e-4 cosine+warmup10），num_chunks=4，factory function 按需建模型避免一次加载 4 个。标称 16–24× experimentation throughput。

口径：这是「多配置对比吞吐」，不是单模型 step/s 加速；无 GPU 利用率数字。

共同的模式

三篇都在解决 实验效率 而非算法创新：数据打包、显存复用、并发调度。它们与 GRPO 主线恰好互补——当算法选型稳定后，瓶颈就转移到「单位时间能验证多少假设」。

6.3 四个常见判断误区

  1. Stars 多 ≠ 能扩。LLaMA-Factory / Unsloth 的 stars 远高于 VeRL，但前者解决「好用」，后者解决「能扩」。用 WebUI 上 256 卡或用 Unsloth 训 70B 全参都会撞墙。
  2. 别把 GRPO 当选型依据。GRPO 已是 commodity，各家都有；真正差异在 orchestration 与规模上限——rollout 生成常占 80%–90% wall clock，谁能让推理引擎不空转才是护城河。
  3. 厂商加速倍数不可直接横比。Unsloth 的 2–5× 基线是 FlashAttention-2；VeRL 的 1.53–20.57× 基线是 2024 年的旧系统；OpenRLHF 反过来测 VeRL 得 1.22–1.68×。自报基准互相矛盾本身就是结论：必须用自己的模型 / 序列长 / 卡数实测。
  4. 实践中的高频路径：先用 TRL / Unsloth 单卡 30 分钟跑通 GRPO 验证算法正确性 → 再迁到 VeRL 放大规模，避免在工程问题上消耗算法迭代时间。

7.3 评估纪律：cookbook 最大的方法论缺口

逐篇核对后，20+ 篇训练 recipe 中没有任何一篇给出完整的定量评测闭环。典型形态是：配 eval_dataset + eval_strategy="steps"，但从不调用 trainer.evaluate() 报告数值；最后展示 1 个 test 样本的生成文本，得出「we've achieved our goal」。

建议补足的四层评估

① 零训练基线：同一 prompt + system message / RAG 的准确率（起点 recipe 已证明这一步可能直接终止项目）。
② 未见样本定量指标：任务准确率、exact match、IoU/mAP（检测）、function-call 参数正确率、solve rate（Agent），并固定随机种子与多次采样。
③ 训练-推理一致性：检查 system message、chat template、tool schema、图像预处理是否完全一致（起点 recipe 与 grounding recipe 都在这里有偏差）。
④ 成本对照：GPU 小时数 / 效果增量，与 prompting、RAG、更大基座模型三条替代路径一起比较。

09选型决策树与分阶段实验路径

Q0 零训练基线能达标吗？（prompting / RAG / 结构化生成 / 换更大基座）
  ├─ 能 → 停止。起点 recipe 第 6 节就是这个结论
  └─ 不能 ↓
Q1 缺口是「格式 / 领域知识 / 输出协议」吗？
  ├─ 是 → SFT + QLoRA（vlm_trl / smol_vlm_sft / xLAM / code_llm）
  │      单卡消费级 → Unsloth / SmolVLM 路线；中文模型 / 要 UI → LLaMA-Factory
  └─ 否 ↓
Q2 有 chosen/rejected 偏好数据吗？
  ├─ 有 → DPO；若 SFT 分布偏移 / 推理不连贯 → MPO（组合损失）
  └─ 没有，但有可验证奖励（答案、单测、规则、环境）↓
Q3 规模与 rollout
  ├─ ≤30B 单机 / 算法验证 → TRL GRPO + vLLM colocate
  ├─ 多轮 Agent / 工具调用 → GRPO + environment_factory + OpenEnv，Jobs 非交互执行
  └─ 30B+ / MoE / 数百卡 → VeRL（或异构资源池选 OpenRLHF）

建议的四阶段实验计划

阶段目标产出 / 决策门
P0 基线固定评测集与指标，跑 prompting / RAG / 原模型一张基线表。若基线达标，项目结束
P1 最小 SFT照起点 recipe 用 1–3B 小模型 + 全量数据的 10%，QLoRA r8，1 epoch对比 P0 的增量；同时验证数据契约、processor、label masking 全链路
P2 规模化全量数据、更大基座、并发多配置 HPO、正式评估闭环成本/收益曲线；决定是否值得进入 RL
P3 RL（可选）先写 reward 的失败路径测试，再单卡 30 分钟跑通 GRPO + vLLM colocate，最后才考虑扩到集群reward 曲线 + 独立评测指标；两者背离即停止
一句话结论

这套 cookbook 的最大价值不是「教会你调 LoRA」，而是提供了一组可对照的最小实验单元：同一数据集（ChartQA / rlaif-v / NuminaMath）、同一 trainer 家族、不同算法层级。把它当「方法谱系的活体索引」来读，比逐篇照抄代码收益高得多；而它的最大缺口——评估与基线纪律——恰好是使用者必须自己补上的部分。
